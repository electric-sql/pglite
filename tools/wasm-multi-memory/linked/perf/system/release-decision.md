# Linked wasm32 release decision

**Keep the portable extension ABI and retain native Wasm multi-memory as the postmaster performance reference.** Both constructors can use the same packaged extension bytes. Classic starts without workers. The linked postmaster keeps a dedicated memory 2 for the session and its parallel workers. These benefits cost no additional changes to the PostgreSQL fork. Postmaster still misses the 10% latency target for HNSW search, hash joins and external TOAST scans. [Four-runtime comparison](release-tables.md) · [Individual runs, plans and package hashes](release-measurements.json)

We compared the linked packages at `b547413` with the native reference at `b788fb7`. Both used PostgreSQL 18.3 at `174b8fcb355e62daa4f265cf4a51d99c8a06a422`, the same PostgreSQL export list and the applicable mixed-loop compiler optimization. The 16 scored runs ran serially, each in a fresh Node 22.13.0 process and database directory, on an Apple M4 Max in OrbStack Linux/arm64. Figures below are medians of four runs. The workloads use warm data, 16 MiB of shared buffers and relaxed durability. [Workload and settings](workload.mjs)

## Where the time goes

**Vector search** improved from 2.18 ms on the earlier linked SDK to 1.45 ms on this release. Native measured 1.17 ms in the earlier comparison and 1.25 ms here. The compiler now groups eight ordered 32-bit reads into one Wasm provider call in eligible loops, preserving the original read order and arithmetic. Single-session HNSW top-10 latency ranged from 1.38 to 1.54 ms linked and 1.17 to 1.36 ms native. At eight sessions, linked served 2,163 searches/s and native served 2,392. Both built the index in about 2.22 seconds. Across the scored runs, every engine used the HNSW index and returned the source vector first in 319 or 320 of 320 self-queries per check. [Ordered-read compiler rule](../../ordered-loads.h) · [Earlier measurements](tables.md)

**Point lookups** took 0.532 ms linked and 0.535 ms native. At eight sessions, linked served 4,749 lookups/s and native served 4,533. The hash join was 22% slower on linked at 12.95 vs 10.62 ms. Both engines used the same query plans.

**Copying inline values** took 1.14 ms linked and 1.09 ms native. A separate four-round trial on the linked postmaster reduced this workload from 2.26 to 1.21 ms by using Node’s bulk Buffer copy after validating the source and destination ranges. The runtime refreshes its views after memory growth and uses typed arrays in environments without Node Buffer. [Copy implementation](../../../../../packages/pglite/src/wasm/linked-memory.ts)

**Fetching external values** remains the largest gap in the storage workloads. A scan that reads one byte from each of 1,024 external 3 KiB values took 5.45 ms linked and 4.12 ms native. Copying and modifying each value took 5.43 ms linked and 4.08 ms native. The harness verified 2,048 TOAST chunks for the external data and zero for the corresponding inline data. Twelve previously profiled external reads made about 5.8 million scalar provider calls and 24,830 cross-heap copies. Reordering scalar dispatch and adding a fused i32 load gave little reproducible benefit. Inlining the global access path at 182,827 sites grew the postmaster Wasm from 14 to 23 MiB with inconsistent timing gains. The next experiment should attribute elapsed time to the scalar accesses during TOAST fetch and identify repeated accesses the compiler can group. [Profile counts](measurements.json)

## Startup and memory

With pgvector and PostGIS registered, linked postmaster reached its first SELECT in 1.76 seconds and native in 2.17. The first CREATE EXTENSION commands for both extensions took 2.87 seconds linked and 2.70 native. Once the cluster was running, opening another session through its first SELECT took 82 ms linked and 169 ms native. With on-demand extension linking, a short aggregate that starts two workers took 91 ms linked and 178 ms native. Process RSS with eight idle sessions was 2,553 MiB linked and 3,955 MiB native. These measurements include the Node workers and compiled Wasm. [Worker startup traces](release-tables.md#startup-diagnostics)

Classic reached its first SELECT in 1.33 seconds on both builds. The classic loader now releases the temporary DSO file buffer after a synchronous load of a verified library. This lowered the linked PostgreSQL linear heap after installing pgvector and PostGIS from 184.4 MiB to 153.6 MiB, matching stock classic. Linked classic started with a 128 MiB linear heap. Total one-session process RSS after installation was 745 MiB linked and 699 MiB stock. [Loader patch](../../sdk/emscripten.patch)

## Qualification and maintenance

- All ten npm tarballs installed in a clean application. All 45 extension archives passed on Node 20.18 and 22.13 with both constructors, for 180 passing runs. Classic created zero workers. Node 20, which lacks native Wasm multi-memory, compiled all 107 Wasm payloads in the audit, including the independent extension probe. The runtime recorded identical pgvector, PostGIS and probe module hashes across constructors. Public SQL checks covered parallel pgvector, cancellation, transaction visibility and PostGIS raster as the first spatial library used in a fresh backend. The existing ICU suite retained one skipped locale test.
- The linked pgvector package is 76 KiB and PostGIS is 14.80 MiB. The corresponding reference packages, which include both target archives and a legacy archive, are 172 KiB and 40.31 MiB. Each linked extension ships one archive. All Wasm lowering occurs in the extension SDK before publication.
- The provider retains its original 167 exports and adds one ordered-read operation. The packager derives its capability requirement from actual Wasm imports. Only pgvector among the release extensions requires it. On both Node versions and both constructors, the new host ran an independently built older extension, and the previous host rejected the new probe with a missing-capability error. Five packaged vector operators matched across 90 size and heap combinations. Separate checks covered read order, bit patterns, bounds, overlap and memory growth. [Compatibility checks](../../sdk/compatibility.sh)
- Both final regression-enabled postmasters passed 230 core and 119 isolation tests, completed 10,000 reconnecting transactions, recovered after an injected crash, and shut down with zero live private heaps. An earlier native stress run dropped a client at 7,851/10,000. Its retry passed and the cause remains unresolved. In a separate parallel-query check, both builds launched two workers from a fresh leader. After the leader had used pgvector and PostGIS, linked still launched both workers and native reported SQLSTATE `58P01` loading `vector.so`. [Qualification results](release-qualification.json) · [Parallel-query reproduction](parallel-leader.mjs)
- Both designs use the same PostgreSQL gitlink and third-party extension C sources. Relative to base PGlite, the common multi-session fork changes 12 PostgreSQL backend files (+220/−62). The incremental maintenance for this work is in the compiler proof, provider ABI, bulk-copy implementation and Emscripten loader integration. pgvector and PostGIS need no hand-written optimization. [PostgreSQL fork ledger](../../qualification/postgres-fork.md)

## Reproduce

The commands below rebuild the linked packages and both regression cores, then repeat the benchmark. The benchmark reads three existing native reference tarballs. Use the pinned revision and native checkout from the historical reference build to generate these tarballs. Their hashes are recorded in the measurement JSON. The PostGIS source build embeds its date in generated SQL, so a fresh build can give a different archive hash. Within one release, both constructors must load the identical archives. Set `PGLITE_BENCH_DEPS` to a directory containing the prepacked `fs-ext-extra-prebuilt` and `nan` tarballs for an offline benchmark install. [Reference build instructions](README.md#reproduce-with-orbstack)

```sh
export DOCKER_CONTEXT=orbstack
tools=tools/wasm-multi-memory/linked
bash "$tools/sdk/build-all.sh" build/linked/replay
bash "$tools/qualification/postgres.sh" build/linked/replay build/linked/replay-postgres
bash "$tools/perf/system/run-release.sh" build/linked/system/packages/stock build/linked/replay build/linked/replay-matrix
```
